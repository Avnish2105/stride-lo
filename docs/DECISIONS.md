# Decisions, interpretations and deviations

The design doc ([DESIGN.md](DESIGN.md)) is the specification. This file records every choice the
doc leaves open, every place it contradicts itself, and every deliberate deviation, with the
reason. If code and this file disagree, one of them is a bug.

Decided on 2026-11-21 with the project owner (Q&A before the first plan).

## Owner decisions

| # | Topic | Decision | Why |
|---|---|---|---|
| D1 | Graph-node requests | `lo_msgs/NodeRequest` input topic. For each requested time, the scan whose span contains it is deskewed to exactly that time and the factor ends there. Without a request topic, keyframes are emitted when overlap with the last emitted frame drops below 90%. | The target backend (`factor_graph_estimator`, GPS-denied repo) creates its own keyframes every 100 ms on Xsens IMU stamps, and plugins add factors at exactly those times. LoFactor stamps must equal node times (doc: "stamp_i = graph node time"). |
| D2 | Scope of integration | This repo only. The GPS-denied repo is not modified. `lo_gtsam_adapter` + `lo_graph_demo` (a node that mimics the backend's keyframing) live here. | Owner choice. Wiring `factor_graph_estimator` (publish pending keyframe times + a LoFactor plugin) is a later, separate change. |
| D3 | Re-INIT after a chain break | Keep the gyro bias and gravity estimate; start a new map from the next scan that passes the checks, even while moving. Only a cold start (boot, crash restart) needs 1 s of standstill. | A walking robot would otherwise get no factors until it stops. Bias still refreshes at every later 1 s standstill. |
| D4 | Build / CI | Standalone workspace: own Dockerfile (`ros:jazzy-ros-base`, multi-arch) with its own GTSAM 4.3.0 build, Livox-SDK2 and `livox_ros_driver2` in an underlay; devcontainer; GitHub Actions. | Owner choice. Same GTSAM commit (`71a25ca3`, tag 4.3.0) and core flags as the GPS-denied workspace so factors behave identically there. |
| D5 | Test data | `lo_synth` (C++ ray-cast simulator, runs in CI), a Python bag fault injector, and a standalone Gazebo Harmonic sensor rig `lo_sim`. | Bags can't live in git; the fault suite must run on every commit. Gazebo scenes add crowd/stairs/180° turn renders. |
| D6 | small_gicp | Pinned upstream (v1.0.1) vendored unmodified in `src/third_party/small_gicp`; fixes as `patches/small_gicp/*.patch`, applied idempotently by `scripts/build.sh` (GPS-denied repo convention). | Upstream `IncrementalVoxelMap` allocates per voxel and its OpenMP reduction is not deterministic: both break hard rules. |
| D7 | Fine map voxel | `0.5·v` (parameter table `voxel.map_ratio = 0.5`), coarse `4·v`. The `1.0·v` registration cloud, with its kNN covariances, is what gets inserted. | The doc says `0.5·v` in S2 and the parameter table but "fine v" in S6. Two of three agree; S4 says the registration cloud's covariances are reused in the map. |
| D8 | Health semantics | `DEGRADED` (1): at least one Hessian-degenerate direction, Σ inflated only on those axes. `LOW_CONFIDENCE` (2): whole-factor inflation — deskew fallback ×4, IMU lost, sensor blocked, factor spans a reject gap, first factor after RECOVERING. The higher value wins. | The doc defines the values but never says when `LOW_CONFIDENCE` is used. |

## Interpretations of ambiguous spec points

| # | Doc text | Implementation |
|---|---|---|
| I1 | "Track the PTP offset and IMU–LiDAR clock skew" | No ROS topic carries the PTP offset. Per stream (LiDAR, IMU) a rolling minimum of (arrival − stamp) estimates latency + clock offset; skew = drift of the LiDAR−IMU difference vs the INIT baseline. Optional `ptp_offset_topic` (`std_msgs/Float64`, seconds) from a PTP monitor. The PTP offset limit is `clock.max_offset` (2 ms, the doc's value); the arrival-based skew proxy has its own limit `clock.max_skew` (default also 2 ms) and switch `clock.check_skew`. Either violated → flag `CLOCK_UNSTABLE` and stop emitting. In replay, arrival = bag receive time (deterministic). **The proxy is off for the GPS-denied sim bags** (`anymal_c.yaml`): their delivery-latency floor wanders by up to 13 ms (yard 1, 2 s rolling minimum: LiDAR 9–20 ms, IMU −5.6–2.2 ms; still 3–7 ms with a 30 s window), so a 2 ms proxy rejected every scan (measured). Sim clocks are exact, and stamp jumps are still caught by the scan validator (I22). |
| I2 | Standstill "joint velocities ≈ 0 and LO motion < 1 mm per scan" | Joints: 0.2 s signed block means of q̇ (the rl_physics robot sways while standing). LO: scan-to-scan registration jitter is 2–7 mm with real range noise (measured, synthetic room), so the 1 mm/scan limit is applied to the *mean* motion over the 1 s window: the mean LO pose of the window's second half minus the first half, divided by the scans between them (noise ≈ 0.4 mm/scan, a 1 cm/s creep shows 1 mm/scan). A per-scan gross gate of 20× the limits (2 cm, 1°) restarts the window on real motion. |
| I3 | IMU lost: "plausibility thresholds tighten by 2×" | All four motion-plausibility limits × `imu_lost.plausibility_scale` (0.5). |
| I4 | `σ̂² = Σρ(r_k)/(N−6)`; GM kernel scale τ/3 | `σ̂² = Σ_k w_k r_kᵀ W_k r_k / (N_inl − 6)`; H includes the weights. The Geman-McClure weight uses the **point-to-plane distance** with scale τ/3: on the Euclidean residual it also punished the expected in-plane offset to the voxel mean (weights ≈ 0.05 → fake degeneracy, 6–25 mm/scan error, measured). |
| I5 | Degeneracy test (`λ_k/N < λ_min` on H scaled by L) | Run on the **point-to-plane Hessian** Σ w (nᵀJ)ᵀ(nᵀJ) (what surfaces constrain; each point adds ≤ 1 to λ/N). On the GICP Hessian, the regularised in-plane "information" times long lever arms made yaw over a bare ground plane look observable → 0.8–2.7° errors with tight Σ (false accepts, measured). Step and covariance use the GICP Hessian restricted to the observable subspace; degenerate directions get σ = 1 m / 0.5 rad through the scaled eigenvector; reported as unit 6-vectors in base-frame `[rot, trans]`. Fine-stage updates are projected; degenerate components of the coarse result are reset to the seed first. `λ_min = 0.02` from synthetic spectra: corridor ≤ 0.010, open field 0.000, crowd p01 0.045, room p01 0.09, warehouse p01 0.10 (re-tune on real bags). |
| I6 | "Rotation vs gyro-integrated rotation over the interval" | Interval = previous processed scan's reference time → current reference time; bias-corrected gyro mapped into the LiDAR frame. Only rejects. |
| I7 | "LRU removal of voxels unseen for 30 s" | Unseen = no insert hit for 30 s of message time. When the pool is full, the least recently hit voxel is evicted. |
| I8 | "scan overlap with the last emitted frame drops below 90%" | Share of current registration points (odom frame) that land in **coarse** voxels (coarse_ratio·v) occupied by the last emitted frame. The Mid-360's non-repetitive pattern hits different fine voxels every scan even at standstill, so fine-voxel overlap would trigger every scan. |
| I9 | IMU sample timing | `imu.sample_convention: instant | interval_mean`. Xsens and the GPS-denied sim publish the mean over (t_prev, t] → sample placed at mid-interval. |
| I10 | "False accepts … never yield a tight wrong factor" | An emitted factor whose NEES vs ground truth exceeds 40 (χ²₆ tail probability ≈ 1e-6). |
| I11 | LoFactor definition | Fields as in the doc, except `T_ij` is spelled `t_ij`: ROS 2 IDL requires lowercase field names. Only constants added (health values, flag bits). |
| I12 | Request mode details | A request is answered from the scan whose span (± `emit.request_tolerance`) contains it, also when it arrives after that scan was processed (I23). Two requests inside one scan: the earlier is answered, the other is missed, because two frames of one registration would make a factor of pure deskew (gyro) motion (hard rule 1). Requests are answered in time order. A request behind the last emitted frame, inside a rejected scan, or more than `emit.request_max_age` (1 s) older than the newest request is missed. An anchor (the first frame of a chain) counts as answered, because the next factor connects it. In request mode the overlap trigger is off (factors must land on graph nodes). |
| I13 | Coarse "wide gate" / RECOVERING "wide-gate"; "no match 2 s" | Coarse stage uses `gate.max`; RECOVERING uses `recovery.gate` (2 × `gate.max`) and its coarse blow-up step limit scales with that gate (0.5 m / 10° rejected every recovery attempt, measured). The 2 s window starts at the first match attempt: scans dropped before matching (clock fault) do not use it up. The seed-deviation check is skipped while recovering (seeds span seconds). |
| I14 | Map content | Gaussian voxels (VGICP style): running sum of points and per-point covariances (S4), count capped at `map.max_pts_voxel` (then frozen, like KISS-ICP), oriented normal for the far-side check, last-hit stamp. |
| I15 | Process crash restart | The node runs as its own process with `respawn`; `lo_supervisor` re-drives configure/activate. A restarted process is a cold start (D3) with a new chain_id (C5). |
| I16 | 8 h soak | 8 h of synthetic data processed offline as fast as possible (fits in a 6 h CI job) with RSS sampled; the real-time soak happens on the robot. |
| I17 | KISS-style adaptive gate τ = 3σ_dev | σ_dev from seed-vs-result deviations of scans that moved ≥ 2 cm (`gate.min_motion`; 0.1 m per scan was never reached at 0.8 m/s). Effective gate = max(τ, `gate.voxel_floor` × fine voxel): correspondences go to Gaussian voxel *means*, up to ~a voxel from any point on the same surface (τ at its 0.1 m floor gave 0.3 inlier ratio in a 30 m hall, measured). Fine-level search is 3×3×3 voxels (fine voxels are 0.5·v, D7). |
| I18 | "Converged when \|Δrot\| < 1e-4 rad and \|Δtrans\| < 1e-4 m" | Once steps are below 10× those limits, correspondences are frozen so Gauss-Newton converges on a fixed set (re-searching every iteration chattered between voxels and missed the 1e-4 limit at standstill, measured). |
| I19 | INIT map | Every registered scan during the INIT standstill is inserted (a single-scan map at 0.5·v voxels gave 0.35 inlier ratio, measured) and the map is kept at the end of INIT; the gravity alignment becomes a fixed output transform (T_align) instead of a map rebuild. INIT holds its map with half the tracking inlier threshold. |
| I20 | DEGRADED map insertion "only with ≤ 1 degenerate direction" | Additionally no insertion while DESKEW_FALLBACK / IMU_MISSING: a constant-velocity deskew may leave rotational smear that must not shape the map later scans are measured against (it produced a false accept right after an IMU dropout, measured). |
| I21 | "Σ_ij ≈ Σ_j for consecutive emissions" | Also composed (Σ_i transported + Σ_j) when frame i itself was DEGRADED / LOW_CONFIDENCE: it is not the well-anchored frame the approximation assumes. |
| I22 | "jumps > 50 ms from the expected period" | One period: ±`scan.period_tolerance` (50 ms). n ≥ 2 periods (scans lost in transport): within ±`scan.drop_tolerance` (20 ms) of a multiple. Anything else is a clock jump. (With a 100 ms period a ±50 ms multiple rule would accept every gap.) |
| I23 | Requests that arrive after their scan | Every accepted scan keeps a `FrameRecord` (ring of `limits.frame_records` = 8): pose at t_ref, registration Σ, and the deskew motion model (33 rotation samples + velocity). The frame at a requested time t in the span is T(t_ref)·D(t) with D(t) = (dR(t), v·(t − t_ref)), and Σ is moved with Ad(D⁻¹). This is the pose that deskewing the scan to t would register: the two deskewed clouds differ by the rigid D(t). Needed because a graph backend answers late. The GPS-denied `/estimator/odometry_keyframe` arrives 34–240 ms after its stamp, so only 20 of 1696 requests were answered before this (yard 1, measured), against 0.988 availability after. factor_graph_estimator waits up to 0.5 s for plugins. |
| I24 | Debug odometry during INIT | No pose is reported before INIT completes: INIT poses live in the INIT-map frame, and the output odom frame (T_align, gravity aligned, yaw 0) exists only from the INIT-completing scan on. Mixing the two gave 10 m "RPE segments" with 150% error (yard 1, measured). |
| I25 | Sim-bag calibration (GPS-denied emulators) | Two test-data parameters, both 0 by default for real sensors, set in `anymal_c.yaml`. (1) `scan.time_quantum` 0.02 s: the emulator takes each point's geometry from the 50 Hz render nearest in time (±10 ms windows) while stamping points continuously, so correct per-point deskew adds up to ω·10 ms of false motion. Point times are snapped to the 20 ms render grid (phase 0 was best of 0/5/10/15 ms). (2) `imu.time_offset` −2.25 ms: the integrated `/livox/imu` gyro matches the 1 kHz `/sim/raw/odom` truth best 2.0–2.5 ms earlier than the interval-mean convention (100 ms windows, bias removed: p50 0.85 → 0.46 mrad, p99 3.7 → 2.0 mrad, rough 1; same optimum on yard 1). Rough 1, request answers: mean NEES 10.4 → 6.5, false accepts 65 → 28. `scan.time_offset` (LiDAR stamps) exists too; its optimum on these bags is 0 (±5 ms sweep). |
| I26 | Graph odometry is an input, not truth | The graph seeds translation and deskews it (allowed by S3/S5), but the GPS-denied estimator diverges on 4 of 15 rough runs (velocities up to 10⁶ m/s from t = 87 s / 110 s on rough 5 / 9). Following it gave 27–52 LOSTs and 0.43–0.80 availability per bag. Gate before use: finite; |v| ≤ `integrity.v_max`, |ω| ≤ `integrity.w_max`; its pose change consistent with that; and its mean LiDAR velocity over LO's last scan interval within `seed.graph_max_dev` (0.3 m/s) of LO's own, compared like for like (LO single-interval velocity noise is ~0.1 m/s, p99 0.33 m/s on yard 1). On failure the graph is ignored for `seed.graph_holdoff` (2 s; diverging estimators pass through plausible values), and seed and deskew use LO's velocity (`SEED_NO_GRAPH`). Rough 9: 1215 rejects / 52 LOSTs → 8 rejects / 0 LOSTs. |
| I27 | Replay methodology on the GPS-denied bags | (1) Requests: `/estimator/odometry_keyframe` is published after the estimator's optimisation (34–240 ms late), but a STRIDE-aware backend publishes NodeRequest at node creation. `lo_replay --request-latency 0.005` delivers each keyframe stamp 5 ms after it (pass-1 prefetch). With bag receive times, late answers move frames along the constant-velocity model by up to 100 ms, which is wrong by cm during trot impacts. (2) Ground truth: `/ground_truth/odom` is 50 Hz, and slerp between samples is off by up to 4.2 mrad (p99 1.7 mrad) at impacts, about one factor σ. `/sim/raw/odom` is the same truth at 1 kHz (identical at the 50 Hz stamps) and is used for NEES. |
| I28 | S3 translation: "graph velocity with the lever arm" | The body rotates about the base origin, so the LiDAR moves by (dR(t) − I)·c, with c = R_blᵀ·t_bl and dR(t) from the gyro, plus v0·(t − t_ref), where v0 is the base-origin velocity in LiDAR axes. This replaces the first-order ω(t_ref) × r·Δt. With the Mid-360 0.6 m ahead of the base, the trot pitch rate reverses inside a scan, and the linearisation sheared the cloud by cm in z. Frame records and late request answers use the same model. Rough 13: false accepts 22 → 0, mean NEES 5.3 → 3.7; rough 1: 5 → 0; rough 14: 18 → 0. |
| I29 | LO's own velocity (seed fallback, deskew fallback, graph gate) | Measured over ≥ 50 ms baselines, not between consecutive reference times. Those can be 7 ms apart (a scan referenced at its end, the next at a request), and 1 cm of pose noise over 7 ms is > 1 m/s: it seeded a 0.3 m error and a LOST on rough 5. The graph gate compares displacements over the last ≥ 0.4 s window (LO noise ~0.04 m/s) with `seed.graph_max_dev` 0.15 m/s. Over one scan interval, LO noise (~0.14 m/s on rough terrain) gated a healthy graph on 595 scans of rough 13; now 0 on healthy bags, while the diverged rough 5/9/10/14 estimators are still gated. |
| I30 | "Converged within the iteration cap" | Correspondences are also frozen from `gicp.freeze_after` (10) on, so the last iterations are Gauss-Newton on a fixed set. Well-conditioned scans (0.9+ inliers) used to oscillate between voxels at the 1e-3 level until the 15-iteration cap, giving 10–20 `not_converged` rejects per bag (~1% availability). The 1e-4 criterion itself is unchanged. |
| I31 | Σ in weakly observed directions | Projecting factor errors onto Σ's eigendirections showed a shape problem, not a scale problem. At κ = 10 the well-constrained directions had normalised squared error 0.16–0.6 (floor-dominated), while the weakest had 1.0–1.7 with a graph seed and 2.5–3.4 with LO's own seed (yard 1, rough 5/14). Correspondences slide along weak directions, so the result keeps part of the seed's error. Added: each observable direction of the scaled point-to-plane Hessian with λ/N < `cov.weak_lambda` (0.2) gets variance `cov.weak_sigma`² (2.5 cm, scaled units) × (λ_w/λ − 1)/(λ_w/λ_min − 1), which is σ_w² at λ_min and fades to 0 at λ_w. Six bags at κ = 20: false accepts 1 → 0. |
| I32 | "Tune κ so mean NEES ≈ 6" vs "0 false accepts" on the sim bags | Not reachable together here: the factor errors are heavy-tailed. Six bags, weak term on: κ 20/8/5 → mean NEES 2.6/3.2/3.4, false accepts 0/3/3. Halving the floor: κ 20/10 → NEES 5.6/7.4, false accepts 20/60. The spec floor (0.05°, 5 mm) is what covers the tail, since real errors in well-constrained directions are 2–3 mm in this sim. Integrity ranks above calibration (hard rule 2), so the sim config keeps κ = 20 with the spec floor: conservative Σ, mean NEES ≈ 2.6–3.1. κ and the floor are to be re-tuned on real ground-truth bags, which the design names as the place to tune them (`evaluate.py --kappa` prints the suggestion). |
| I33 | lo_sim sensors (D5 "standalone Gazebo sim") | Gazebo Harmonic runs the world (generated from the lo_synth scenario by `lo_sim_world`), the clock, and the `KinematicRig` system plugin that moves the rig and the crowd exactly along the scenario. The sensors are emulated analytically by `lo_sim_rig` (lo_synth ray caster: Mid-360-like pattern with exact per-point times, Livox IMU in g, joints, URDF, ground truth), not by `gpu_lidar`. The container has no GPU (`/dev/dri`), and the design notes that `gpu_lidar` has no per-point timing, so it could not validate deskew. Analytic sensors are exact, deterministic and run headless; `gazebo:=false` makes `lo_sim_rig` the clock source. Live crowd run with Gazebo: RPE 0.076 %, NEES 1.38, 0 false accepts. |
| I34 | What the GPS-denied bags' IMU errors mean for the calibration | The bags were recorded with `imu_errors:=realistic` (`quadruped_gazebo/config/sensors/livox_mid360.yaml`). For the Livox IMU that profile adds driver stamp latency 2 ms + 0.5 ms jitter, drops, foot-impact ring-down (1.5 g, 0.3 rad/s at 80 Hz), 0.5° mount misalignment, turn-on/warm-up/thermal bias, 1000 ppm scale and g-sensitivity. The measured `imu.time_offset` −2.25 ms (I25) is therefore the emulated driver latency, a real-world effect and not an emulator artifact. On hardware it must be re-measured (`time_offset.py`, no ground truth needed). The other terms stay below ~1 mrad per scan in the deskew; bias is estimated at standstill. They add to the heavy NEES tail (I32), which is why κ was not lowered to fit these bags. Sim-only settings are confined to `anymal_c.yaml`: `scan.time_quantum` (a 50 Hz render artifact), `imu.time_offset`, and `clock.check_skew: false`. Nothing else is fitted to the sim. |
| I35 | Deskew fallback "Σ × 4" on a trotting robot | Bag fault suite, rough 1, first 100 s. Clock jump, point dropout 50 %, lens blocked, leg points and IMU vibration (3.5 m/s², 0.05 rad/s): 0 false accepts, availability ≥ 0.94 (the clock jump forces the designed chain break). IMU dropout 1.5 s: 7 false accepts despite LOW_CONFIDENCE and ×4. Without the gyro, the constant-twist deskew cannot follow the trot's roll oscillation inside a scan: 25–40 mrad roll errors against σ ≈ 3 mrad, while translation stayed within σ. Added `cov.fallback_rot_sigma` (0.05 rad) to the rotation block whenever DESKEW_FALLBACK: 7 → 0 false accepts, availability unchanged at 0.998. PTP drift (2 ms/s for 5 s): 1 marginal false accept (NEES 45), because the sim config has the arrival-based skew check off (I1). On hardware this drift is caught by `topics.ptp_offset` or `clock.check_skew`. |
| I36 | Rule 1 "the map is built only from LO poses" vs a readable RViz demo | `lo_sim/lo_viz.py` is visualisation only: it subscribes to STRIDE outputs and ground truth, and publishes only TF (`world→stride_odom`, `world→graph_odom` = GT(t₀)·pose(t₀)⁻¹ at the first pose; `stride_odom→base` from `/stride_lo/odometry`, `publish_base_tf:=false` where another node owns `base`), paths and a status marker. STRIDE subscribes to none of these. The RViz robot model uses a separate viz URDF (`lo_sim_world --urdf`, on `/lo_viz/robot_description`), so the self-filter's `/robot_description` input is unchanged. `debug.publish_deskewed` is on only when RViz is (debug output, not in the factor). |
| I37 | Gazebo sim went LOST (clock_unstable) | The causes were in the test rig, not STRIDE (it rejected correctly; the false accepts are I38). (1) `lo_sim_rig` ray-cast each scan when it was due (single thread), so scans left 30–69 ms late (CPU-load dependent, crowd) while IMU samples caught up at once: a real LiDAR–IMU arrival skew. Now a producer thread simulates up to `lookahead` (0.5 s) ahead and a release thread publishes every ready-built message at its arrival time: skew ≤ 3 ms with both GUIs on. (2) Gazebo's bridged `/clock` drove time and jittered with GUI load. Now `lo_sim_rig` always owns `/clock` (monotonic wall timer, 1 kHz) and Gazebo's `KinematicRig` follows it over a ROS→gz bridge (`/stride/scenario_clock`): Gazebo is display only (supersedes the clock part of I33). It also writes the Pose component directly: the world runs no Physics system, so the old `SetWorldPoseCmd` never moved anything. (3) llvmpipe used every core (Gazebo GUI 631 %): viewers now run `nice -n 10` with `LP_NUM_THREADS=2`. `stride_rig.yaml` sets `clock.max_skew: 0.015` above the remaining ≤ 3 ms and keeps the check on (off, a 50 ms LiDAR offset gave 38 false accepts). Live crowd, Gazebo GUI + RViz + recording, 146 s: before 20 LOSTs, 1126 clock_unstable rejects, availability 0.170, 3 false accepts, RPE 13.4 %; after 1 LOST, 0 clock_unstable, availability 0.966, 0 false accepts, RPE 0.095 %, NEES 1.49. The remaining LOST (t ≈ 123 s, 5 rejects from walkers) is identical in the ROS-free synthetic run and recovers in < 1 s. |
| I38 | RECOVERING after a long gap | I13 does not count clock-fault rejects against the 2 s recovery window, so a recovery could bridge an arbitrarily long gap with one factor. After an 11 s clock fault the wide-gate match locked 6.7 m off along a degenerate axis (σ inflated to 1 m): NEES 2690. New `recovery.max_bridge` (2 s, the doc's recovery window): a recovery after a longer gap since the last accepted scan keeps tracking but starts a new chain, so no factor bridges the gap. Synthetic crowd with clock_jump faults (5 cases: 1 s to 12 s, 0.05 to 0.5 s offsets): false accepts 4 → 0, availability −0.001 at most, mean NEES 393 / 20.9 → ≤ 1.49. |
| I39 | `lo_graph_demo` crashed (GTSAM IndeterminateSystemException) after a chain break | A new chain's prior was σ 10 rad / 1 km; with a DEGRADED first factor the system became indeterminate. The prior is now σ 0.5 rad / 10 m, and any solver exception restarts the graph at the last estimate (path kept) instead of killing the node. Replaying the factors that crashed it: 199 factors, 1 chain break, 0 restarts. Demo node only; the real estimator bridges chains with IMU factors. |
| I40 | "Replace FAST-LIO" | STRIDE is not a drop-in: it emits relative LoFactors at backend node times, and `~/odometry` stays debug-only (never fused, rule 2). Integration = the backend publishes NodeRequest at node creation and adds `lo_gtsam_adapter::toBetweenFactor` (with body_T_base) per usable factor, bridging chain breaks with its own IMU factors. With no backend yet, `lo_graph_demo` (`~/pose` with marginal covariance) is the LO-only pose source. Contract: INTEGRATION.md; consumer proof: `examples/minimal_backend` + `check_consumer.sh`. The GPS-denied repo is wired by its owner, not from this repo. |

## Deviations from the doc's package list

- `lo_synth` (ROS-free simulator library) and `lo_sim` (Gazebo rig) are added (D5).
- `src/third_party/small_gicp` + `patches/` (D6).
- `lo_gtsam_adapter` also hosts the `lo_graph_demo` node (D2).

## Environment facts the design depends on

- Target backend: `factor_graph_estimator` (GPS-denied repo). IMU-centric (MTi `/imu/data`
  500 Hz in sim), state = IMU frame, keyframes every 100 ms on IMU stamps, ISAM2 fixed-lag 3 s,
